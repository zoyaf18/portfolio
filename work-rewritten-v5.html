what I’ve learned

A powerful capability becomes a product only when people know where it fits.

Working on enterprise AI has made me think beyond whether a model or agent can perform a task. The more interesting questions are often: Where does this belong in the workflow? How much should the system decide for the user? Where should users retain control? How do we know the output is good enough? What happens when cost, capability, latency and usability pull in different directions?

Those questions increasingly shape how I approach both engineering and product decisions.

model intelligence · initiative owned

Making the default smarter, without taking control away.

As more models became available, model choice became its own product problem. Different workflows needed different levels of reasoning and capability. Using the most capable model everywhere increased cost unnecessarily, while relying too heavily on lighter models could affect quality on complex tasks. Expecting every user to understand the model landscape also created friction.

I proposed, researched and owned the model auto-router from concept through rollout: building the case for the approach, securing leadership buy-in, studying routing strategies and model behaviour, implementing the capability, and working with DevOps on the changes needed to take it into production.

The router uses signals such as task complexity, model capability and caching to make an intelligent default selection, while users can still override the system through simpler model choices when they want more control.

The work enabled higher-capability models to be used more selectively and helped reduce token cost by 36% while maintaining output quality across the evaluated workflows.

AI quality · evaluation system

Turning “this response looks good” into something we can actually test.

Generative AI changes what quality assurance looks like. A response can be technically valid and still be incomplete, poorly grounded, inconsistent or simply not useful enough for the workflow it serves.

I proposed, researched, built and owned an evaluation framework for production-grade AI outputs, combining multiple layers of validation rather than relying on a single score.

Golden dataset. Representative inputs and expected behaviours create a stable regression baseline, so model, prompt or workflow changes can be retested against the same important scenarios instead of being evaluated ad hoc.

Deterministic gates. Machine-verifiable checks cover schema and JSON validity, required fields, formatting rules, expected tool calls, prohibited output, exact workflow constraints and response completeness before subjective quality is considered.

LLM-as-a-judge. A rubric-based evaluator scores qualitative dimensions such as relevance, instruction adherence, usefulness and overall response quality where deterministic checks are not enough.

Continuous user feedback. Production feedback surfaces failure modes that offline evaluation can miss and helps turn real user issues into future regression cases.

Together, the system creates a loop: golden cases → deterministic checks → qualitative evaluation → production feedback → better evaluation cases.

I also built automated debugging and validation agents for our internal AI tools, reducing manual debugging effort by 50% and QA preparation time by 65% while improving test coverage.

product enablement · user adoption

Helping users choose the right intelligence for the job.

Giving people access to multiple models is useful only if they understand when each one belongs in their workflow. I created model-selection documentation and delivered demos that translated differences in model capability, behaviour and cost into practical workflow decisions.

Instead of explaining models as a technical catalogue, I focused on the questions users actually needed answered: What kind of task am I solving? How much reasoning does it need? When does a stronger model meaningfully improve the outcome? When is a lighter model already enough?

Those conversations also became product input. The questions users asked showed where model differences were unclear, which trade-offs they cared about, and where better defaults, terminology or guidance could reduce unnecessary decision-making.

I fed those signals back into product discussions alongside engineering constraints and usage patterns, connecting user education, product design and model strategy rather than treating them as separate problems.

agent platform

Giving teams primitives they can shape around their own use cases.

The web platform is designed around a simple idea: different teams need different kinds of AI behaviour. Rather than prescribing one fixed workflow, the platform provides composable capabilities such as context, reusable skills and human-in-the-loop controls that teams can combine around their own use cases.

Working on a platform like this means constantly balancing abstraction and flexibility. Too little structure and every team has to solve the same problems again. Too much structure and the platform stops fitting the workflows it was meant to support.

My work spans feature development, defect resolution, UX feedback and validation, but also the product conversations around which capabilities should become reusable platform primitives, how much configurability users need, and where human oversight should remain part of the experience.

I work with users, engineering, QA, DevOps and UX throughout that cycle — from requirement refinement and technical feasibility through validation and rollout.

AI developer CLI

Bringing AI into the developer workflow, not beside it.

The second product is a company-wide AI CLI used by roughly 1,200 developers. I contribute to capabilities such as pre-built skills, custom skills and memory, designed to let developers adapt the tool to their own workflow rather than repeatedly recreating context and behaviour.

A developer tool creates a different kind of product discipline. Every extra interaction is noticeable. Unpredictability quickly erodes trust. Power matters, but so does staying out of the user's way.

That means the experience has to feel fast, composable and predictable enough to become part of how someone already works. I bring feedback from users and hands-on product use into feature discussions and prioritization, while working across engineering and validation to make sure those ideas survive contact with the actual system.

0→1 product · BloodNet

Reframing emergency blood availability as a coordination problem.

BloodNet started with a deceptively simple question: if someone urgently needs blood, why is the problem treated primarily as finding a donor? Availability actually depends on several moving parts — existing inventory, compatibility, location, donor responsiveness, urgency, approvals and regional supply.

So I reframed the problem around coordinating the fastest reliable path to fulfillment and designed the product around the critical loop: request → inventory → shortfall → approval → donor mobilization → resolution.

AI and ML support extraction, ranking, forecasting and investigation, while consequential inventory and fulfillment actions remain human-approved. The product spans multiple stakeholder journeys across hospitals, blood banks, donors and regional operations, and extends beyond reactive matching through Blood Weather, which forecasts potential regional shortages before they become emergency requests.

The product also changed through user feedback. When early users struggled to understand a login-first experience, I redesigned the entry journey around a public regional dashboard that explains the system before asking users to enter it. Follow-up testing showed substantially clearer comprehension.
